# 踩坑与优化点（复盘）

> 每一条都对应一次真实的走弯路。下次跑分前过一遍这份清单。

## 一、流程类

### 1. 前置检查被跳过 = 全部白跑
VPN 不通时，平台 API 仍可能返回 200（公网可达），很容易误以为"能跑"，
结果所有 `container_addr` 都连不上，浪费大量时间。
**结论**：只认内网健康检查地址，通则不跑。

### 2. 并行度没吃满
前 30 分钟串行做，每题 3-5 分钟，等于损失 2/3 吞吐。
**结论**：拿到题目列表后 **5 分钟内**就要按平台上限把流水线拉起来（默认 3，409 自动学习；不要写死 3）。
约束写进 subagent 的 prompt：每人只占 1 个容器、做完立刻 close。

### 3. 套路没有回流，第二轮又从头摸
第一轮 agent 各自摸索，第二轮把"已验证套路"写进 prompt 后，命中率明显上升。
**结论**：每轮结束花 2 分钟提炼"指纹 → payload"，作为下一轮的输入。

### 4. 环境缺失被当成"再试试"
有一题应用侧报 `getaddrinfo failed`（连 `mysql_db`），这说明**目标容器内的 DNS 解析失败**，
即依赖服务没被编排起来，不是本机缺 MySQL。
判断依据：
- `Class 'mysqli' not found` = 扩展缺失（可补救）
- `Connection refused` = 端口在但服务没起（可等）
- `getaddrinfo failed` = **服务不存在**（放弃）

而且 flag 只在 DB 里时，任何 RCE 也没用——先确认"flag 数据在哪"，再决定打不打。

### 5. 时间盒失效
hard 题上磨了 35 分钟，最后没出。
**结论**：start 时就设闹钟（easy 5 / medium 10 / hard 20 分钟），到点 close。

## 二、技术类

### 6. 竞态：单发编排永远打不中
第一次实现是"发 1 个受害者 + 1 个写者"。理论上窗口 40ms，实际上：
- 服务端多 worker，同一会话只有 1/N 概率落到同一 worker（实测 10%）
- 两个请求的网络到达时间本身就有抖动

实测 150 轮 0 命中。改成 **每轮 12 个受害者 + 6 个写者，起始时间在 0–50ms 内错开**，
40 轮内命中。概率从 ~1% 提到 ~30%/轮。
**教训**：概率型漏洞要靠"并发铺开 + 时间抖动"，不是靠"多试几次"。

### 7. 概率型题的前置状态必须每轮重建
竞态里第一个写请求成功后就"毒化"了会话（username 变成 admin，校验必失败），
后续所有请求都会在第一步就被拒。
**教训**：`prepare()` 必须每轮重新登录/重建会话。

### 8. XSS 回显是"诊断信息"而不是"失败提示"
看到 `TypeError: Attempting to change the setter...` 时，第一反应是"payload 被过滤了"，
实际是 payload **根本没执行**（反射上下文判断错，比如在 JS 字符串里塞了 HTML 标签）。
**教训**：先判断上下文（文本/属性/JS/URL），再选载荷；失败信息要读原文。

### 9. Django SSTI 不能用 jinja 的链
`{{''.__class__}}` 直接 `TemplateSyntaxError: Variables and attributes may not begin with underscores`。
正确入口是 `{% debug %}`（dump context，常常直接出 flag）和
`{{messages.storages.0.signer.key}}` 这类无下划线属性。
**教训**：先花 10 秒确认模板引擎（`{{7*7}}` vs `{{7|add:7}}`），再选 payload 族。

### 10. Apache 的 403 不等于"拿不到"
`<Files "flag"> Require all denied` 只挡直接访问；
应用自己的 `send_from_directory` / 读文件接口往往能读到同一目录。
**教训**：403/404 之后问一句"还有没有别的读文件的入口"。

### 11. LFI 过滤是"顺序 str_replace"
`str_replace(['../','./'], '', $x)` 这类实现，`....//` 会先变 `../` 再被 `./` 吃掉；
而 `...././/` 在第一遍替换 `../` 后残留 `../`，第二遍 `./` 扫描位置已过，能活下来。
**教训**：过滤器实现方式决定绕过串，别背通用 payload。

### 12. 日志投毒别写双引号
UA 里带 `"` 会被 Apache 转义成 `\"` 写进 access.log，导致 include 时 PHP 语法错误，
且该日志**永久损坏**，只能重启容器。
**教训**：投毒 payload 只用无引号形式：`<?php system($_GET[0]);?>`。

### 13. 上传题的判定维度要对齐
- 判扩展名尾串 → `x.php.jpg` / `x.pdf.php`
- 判 Content-Type → 加 JPEG magic `\xff\xd8\xff`
- 判 `file_exists` → 用 `//tmp/x` 双斜杠绕过再 `phar://`

### 14. 多服务题先确认"flag 在哪个服务里"
有的题 flag 只在 DB、有的在 env、有的在文件。
拿到 RCE 却读不到 flag，往往是打错了服务。
**教训**：源码里 `grep -rn "FLAG\|flag"` 确认注入点，再决定打哪层。

## 四、"结论级"教训（最贵，必须写死）

### 15. 不要接受"这题不可解"的结论 —— 包括我自己下的
本轮的两次误判，成本都是 300~500 分：

- **误判 A（假阴性）**：一次把"依赖服务 DNS 解析失败"直接当成"平台缺陷、放弃"，
  没有自己复核。正确做法是找一个**同平台的对照组**证明"同类服务在别处是通的"，
  再断言"是这道题的编排问题"。
- **误判 B（更贵）**：一次接受了"竞态被 ORM 缓存挡住，理论不可行"的分析，准备放弃；
  后来只是**换了并发编排**（12 受害者 + 6 写者、起始时间抖动）就命中了。

**写死的规则**：
1. 任何"不可解"结论，必须由**我本人**用最小可复现实验证一次，不能引用他人结论。
2. 概率型（竞态/爆破/时序）的失败，**首先怀疑并发模型**，其次才是"理论不可能"。
3. 断言"环境缺失"时必须给出可证伪证据：对照组、端口扫描、解析错误原文三者至少其一。

### 16. 子任务要隔离工作区
多个执行体在同一目录并发跑，产生了上百个临时脚本和 1GB+ 的下载物，
既污染工作目录，也让后续检索变慢。

**写死的规则**：派发 subagent 时指定 `cwd=$PI_WORKBENCH/work/<code>` 这类独立目录，
结束要求其自清理；只把"结论"和"脚本"回流，不要把靶场源码/压缩包留在主目录。

### 17. 探测输出必须截断
早期直接把 Django DEBUG 页、目录列表吐到终端，单次几千行，纯烧上下文。

**写死的规则**：探测阶段一律 `grep -i "flag\|error\|title" | head -30`，
或走 `framework.net.Response.brief()`；完整响应只在定位到具体线索后再取。

## 五、多题短周期复盘（去标识化）

一轮 37 题的闭卷跑分，easy 全收、medium 过半、hard 约一半。
下面只写**下次会改变行为**的结论，按代价排序。标签 A/B/C… 是当局题目，已隐去平台与编号。

### 18. 最大失分点不是“不会做”，是**长尾阻塞**（估计损失 30-45 分钟 × 1-2 个容器名额）
3 个 worker 用 `Promise.all` 派发 → 必须等**最慢的那个**结束才能发下一批。实际形态：一个 worker 跑了 ~110 分钟（APK native 逆向），另两个各 ~40 分钟，占着 1-2 个容器名额
近一小时，而同期最快的题 4 分钟就能交。

**写死的规则**：
1. 派发用**滚动补位**，不要 batch-and-wait：任一 worker 结束立刻补新题；
2. 时间盒设了不等于会停 —— subagent 会自述超时后继续干。**主 agent 每 5-8 分钟
   拉一次 `/challenges`，看 `container_status=available` 的题超时了就 `close`，
   主动回收名额**（close 后 worker 的请求全失败，会自然收尾）；
3. 派活时把“容器名额只有 3 个，超时 = 偷别人 200-900 分”写进 prompt。

### 19. 主 agent 不要亲自攻坚
开局我亲自打了 题A（对象存储路径穿越）**13 分钟 0 分**，交给 worker 后 3 步解出。
**规则**：主 agent 只做排产 / 交付 prompt / 轮询回收；任何“我要不要自己打一下”的念头
都是排产失误。

### 20. 容器 IP 复用 + 启动抖动，吃掉 hard 题 30-50% 的时间盒
现象：`start` 返回两个地址，**顺序会互换**，且 IP 池滚动复用（上一条命令拿到的
`:80` 下一条可能变成另一道题的 app）。多题出现“6 次 start 全部无监听”。

**写死的规则**：start 后 15 秒内跑统一探活：两个地址都做 TCP + `GET /`（带浏览器 UA），
比对 title/`Content-Disposition` 与题面对齐；不通就地再 `start`（最多 3 次），
**不要**做 /24 全网扫描（本轮有一个 worker 扫了 255 主机，纯浪费）。
模板：`$PI_WORKBENCH/work/probe13.py`。

### 21. 默认 UA 会被 edge WAF 403
`curl` / `python-requests` UA 在部分题会拿到 `403 {"reason":"client blocked","layer":"edge"}`，
被误判成“路径不对/无源码”。**规则**：所有请求默认带浏览器 UA。

### 22. hard 题的第一动作固定为“拿源码 / 拿前端 bundle”
本轮 hard 成功的 11 题里，**7 题是靠 `GET /` → `src.zip`/`root.zip` 或 `Vite /src/**` 直接读到源码**
（题B/13/14/15/25/29/30，单题 4-10 分钟）；而失败的黑盒摸索题（01/18/23/24/27/34/35）
全部卡在“猜路由/猜状态机”。
**规则**：hard 优先选**能拿到源码的**；拿不到源码的 hard 排到最后，盒子给 10 分钟就换。

### 23. 已沉淀的可复用链条（直接抄，别重推）
- 命令注入：`%0A` 换行 + `$IFS` 代替空格 + `/fl?g` 通配绕关键词 + 写 `/app/public/` 后经 `/static/` 读回（题C/题D）；
- WAF 路径黑名单：用 `\` 或 `%5c` 代替 `/`（题E）；
- 签名类：`sign_type` 不在签名参数集里 → 可自由声明 MD5；验签密钥 = `base64(DER 公钥)` 且公钥由接口公开 → 可伪造回调（题F）；
- 金额逻辑：校验用 int64、结算用 int32 → 构造 `Σ(line) mod 2^32 ∈ [coupon, coupon+wallet]`（题G）；
- Android 静态：`SHA-256(签名证书 DER)` 做外层 XOR key + Base64 常量内层（题H/04/06/07/19 五连中）；
- 伪造 LLM 端点：自己起 mock `/v1/messages`，按轮次返回 `tool_use` 让 Agent 读文件（题I，3/3 flag）；
- 鉴权：capability/ref 不绑主体 → `resolve` 逐层拿 parent_ref 再 `lookup` 不过脱敏（题B/题J）；
- Next.js：`x-middleware-subrequest: middleware×5`（CVE-2025-29927）；URL guard 用 `http://allowed@127.0.0.1:PORT/` 绕过（题K/题L）。

### 24. 提交纪律：先自证，再提交（本轮 2 次错提交）
题M 解出 `flag{REDACTED}` 被判错、题N 拿证书哈希冒充 flag 被判错 —— 两次都是
“解密链没闭环就提交”。**规则**：
1. 静态解出的 flag 必须能用**第二条独立路径**交叉验证（另一处密文/服务端接口/协议回显），否则先别交；
2. 拼接类题先确认分段顺序再有把握地交；
3. 单题错误提交 ≤2 次，之后必须换思路；只在“差一点且分高”时考虑 hint（题O 用 hint 700→630）。

### 25. 本轮确认的“不可解 = 部署缺陷”（有证据，下次别重试）
- 题P：RCE 已拿到（Flight 反序列化 + WAF 绕过），镜像内**没有 `/flag`**，`/root` 700 不可读，`ledger` 只有 `/health`；
- 题Q：容器下发的是另一道题（「墨记·轻博客」），题面应用未部署；
- 题R：`/admin` 存在但全站**无发帖/回帖入口**，用户内容无法进模板；
- 题S：actuator + Jolokia Tomcat MBean 都可控，但根文件系统只读，无法落 `web.xml`/JSP。
→ 这 4 题应当**当场 close 并跳过**，而不是各花 10-15 分钟。

### 26. 框架自身（已修 / 待办）
- [x] `framework/net.py`：`Set-Cookie` 大小写 + 多值合并 bug（多 cookie 站点登录态丢失，本轮让 题T/题R 各卡 5 分钟）；
- [x] `framework/cli.py run/auto` 已内置“start → 双地址 TCP 探活 → 指纹 → 打印”，见 `framework/governance.py`；
- [x] `--watch` 已实现：默认只警告；`--close` 仅在“超时+宽限+空闲”时关闭；`--hard` 才到点无条件（不推荐，见第 40 条）；
- [ ] `submit` 失败时自动打分/提示“是否用第二条路径验证过”。

## 六、大卷面复盘（去标识化）

一轮 63 题、约 4 小时的闭卷跑分，拿到九成以上分数。
下面每条都是「当时白烧了时间 → 后来写死的规则」。

### 27. VPN 层是最前置的单点，且“修它”本身会把它弄坏
三层坑叠在一起，白烧约 15 分钟 + 一段断网：
1. `openvpn-gui` 在跑但连的是**旧 profile**（且已断开）→ 必须重启 GUI 让它重扫 config 目录，再 `--command connect <name>`；
2. 有**两个 TAP 网卡**：上一轮残留的旧网卡（metric 25）还挂着推送路由，新连的（metric 281）抢不过 → 包全进死接口。此时 `curl --interface <新网卡 IP>` 能通，是确认“到底是 VPN 还是路由”的判据；
3. 提权 `netsh interface set interface ... admin=disabled` 停掉僵尸网卡后，**推送的 5 条路由被一并删除**，整条 VPN 断，容器全不可达。

**写死的规则**：
- 动网卡前先 `route print -4` 存档；**不要在 VPN 会话期禁用任何 TAP**；
- 唯一正确的重连姿势是 `openvpn-gui --command disconnect <p> && --command connect <p>`，让 OpenVPN 自己重建整套路由；
- 恢复后用 `route print | grep <vpn-check-host>` 确认 /32 路由在，再继续跑分。
- 无管理员权限时：`Start-Process -FilePath cmd.exe -ArgumentList ... -Verb RunAs -Wait` 可以触发 UAC 提权（本轮成功）。

### 28. 最大失分点：「缺凭据型」卡点无限堆字典（本次 ≈ 45 分钟 0 分）
题U 拿到 2/4 flag 后，为剩下 600 分又投了 **3 轮**：14106 组口令打 panel 登录、900+ 组打 SSH、内网全扫、LFI+RCE 全上 —— 边际收益 **0**。同一时间窗口 worker 刷掉 题V/题W/题X/题Y（1400 分）+ 题Z/题26（1000 分）。

**写死的规则**：
1. 单题**两轮 0 新增 → 立即 close**，写进笔记标记 dead-end；
2. 识别“卡点是凭据”时，先问“凭据应该从哪来”，找不到来源就别爆破（来源可能是另一台机器的 dashboard）；
3. 每 10 分钟算一次分/分钟，低于当前中位数的题直接放弃。

### 29. 坏题被反复重派（题27 三次 / 题28 两次 / 题29 两次 / 题30 三次）
每次重验 5-15 分钟、零收益。

**写死的规则**：
- 维护 `work/SKIP.txt`，坏题结论一次落盘即排除；
- 坏题自检标准化为 **60 秒门**：`POST` 是否 501 / `/login` 是否恒 500 / 全端口是否只有一个映射端口 / `start` 是否只返回 1 个 addr —— 命中即 close，不投入时间盒。

### 30. 反向 relay 必须做“负向验证”再信结果（题31 白烧 3 轮）
连环 bug：`pkill -f 'zf.pl'` 把自己的 `bash -c` 包装进程一起杀了（relay 根本没起）；Windows 侧重复 bind 同一端口会让 relay **静默失效**；单连接 relay 让 paramiko 拿到死连接（`Error reading SSH protocol banner`）。

**写死的规则**：
1. `pkill` 要锚定 `^perl /tmp/xx`，不要裸匹配脚本名；
2. 每轮换端口，不要复用；
3. **搭好通道先用一个必然错误的凭据连一次**：必须收到 `AuthenticationException`（而不是 banner 错误/EOF），否则说明通道没通，此时所有“密码不对”的结论都是假的。

### 31. 并发 worker 共用 work 目录会互相覆盖
`rce.py` / `relay.py` / `h.py` 被别的 worker 中途覆盖，链路直接断掉，只能全部重命名成 `b01_` 前缀重来。

**写死的规则**：派活时就在 prompt 里写死“所有文件必须带 `<code>_` 前缀”，或每人一个 `work/<worker>/`（对应第 16 条，但本轮证明光说“隔离”不够，要给命名约定）。

### 32. 容器内网拓扑每轮漂移
同一题不同实例：容器网段里的角色会互换（`.2`/`.4`），网段号也会漂移。照上一轮笔记打的人全打空。

**写死的规则**：start 后固定动作 `getent hosts` + 扫 `/24`（用容器内 `tunnel.php?action=scan&ports=...`，一次 2-3 秒）；笔记只写“方法/角色”，**不写 IP**。

### 33. 报“参数缺失”时先怀疑字段名，别先换 payload
题32 真实 JSON 字段是 `target_endpoint`、题33 是 `target_url`，前端写的是 `url`。**两题各卡了两轮**。

**写死的规则**：`{"error":"xxx is required"}` + 参数明显给了 → 用“父词×子词×连接符”（`target/source/endpoint/uri/link/path/url` × `_/-/./拼接`）生成 1000+ 候选一次爆完，比跑 SecLists 单词表有效（`work/a14p5.py`）。

### 34. 注入 shell 的重定向作用域
`0=a; b; c > file` 只有 `c` 的输出进文件，我一度以为命令没执行。
**规则**：注入长命令一律 `( ... ) > file 2>&1`。

### 35. PHP 长任务会被 `max_execution_time`（30s）砍掉
14106 次爆破放在 `include` 里跑，请求超时返回空，看起来像“脚本没跑”。
**规则**：长任务一律 `nohup php /tmp/x.php > /tmp/x.log 2>&1 &` + 写 `*_prog.txt` 进度文件，再轮询读取。

### 36. `curl_multi` 循环的终止条件
`while ($running || $found==='')` 会死循环；改成看 `$total < $n` 又因为 `$running` 瞬时为 0 只跑 24 个就退。
**规则**：按“已完成总数”判终止，并按批次（batch）而非流式，最稳。

### 37. GBK 控制台的编码坑
中文 JSON 一 `print` 就 `UnicodeEncodeError`；脚本里写 `b"文件不存在"` 直接 `SyntaxError: bytes can only contain ASCII`。
**规则**：一律写 UTF-8 文件再用 read 工具看；需要判断中文字面量时用**长度**或转义字节，不要直接写中文进 bytes 字面量。

### 38. 平台按 flag_index 去重，且 flag 每实例随机
换容器后同一个 index 不能重交（`409 duplicate`），必须在新容器里重新取；`correct_flag_count` 只按 index 计数。
**规则**：多 flag 题每次 start 都重新取全部 flag；提交后看 `matched_flag_index` 对齐，别把旧值当新 flag 交。

### 39. hint 成本要事先算，不要撞上了才想
题31 有 worker 先看了 hint，导致后续 flag 从 300 变 270（累计少 60）。这次 hint 内容（“文件服务器就是泛微 OA 管理员后台”）确实直接帮助多了 2 个 flag，**算回本但不该是碰运气**。
**规则**：每题开打前决定“这题要不要看 hint”，写进派发 prompt；已看过 hint 的题，剩余 flag 已按比例折价，可以放心再读一次（不再二次扣）。


### 40. 时间盒不能做成“到点无条件 close”
把时间盒直接实现成 `sleep(N); close`，会误杀“正在做、只是没写文件”的题：
模型可能正在等一个慢回包、在脑内推链、或在读一份大源码；这些都不会产生 `work/` 文件活动。
一旦 close，容器和已拿到的中间状态全没了，重开还要重新打。

**写死的规则**：
1. 时间盒是**软提醒**：软截止只提示“停止开新方向”，不关；
2. 分层：easy 5/10、medium 10/20、hard 30/60、credential 5/5、intel 20/45；
3. 只有“硬截止 + 空闲超过阈值”才建议/执行 close；`--hard` 才是硬截止无条件关；
4. 延长用 `extend <code> 10m "新原语/里程碑"`，主控批、最多一次；`touch` 只在新原语时用；
5. 要保题就 `hold <code>`，看门狗绝不关；默认 `--close off`，只警告。

### 41. SKIP 不能只写在文档里
“坏题只验一次”写在 SOP 里时，实际仍出现 题27 被 3 个 worker 各验一遍、题30 三次、题28/题29 各两次。
根因不是不知道规则，而是**派发时没有可执行的检查点**。

**写死的规则**：
1. 派发前先 `python -m framework.cli check-skip <code>`（exit 0=已跳过，1=未跳过）；
2. 确认坏题后 `python -m framework.cli skip <code> <证据>`，写入 `work/SKIP.txt`；
3. `next`/`run`/`auto` 自动排除 SKIP，只有 `--force` 才重试；
4. 坏题自检 60 秒门仍保留；命中即 skip，不投入时间盒。
